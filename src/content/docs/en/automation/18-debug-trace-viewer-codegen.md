# Debug, Trace Viewer & Codegen

QC Training Documentation - HR Tool

Sooner or later, every automated test will fail — the question is how fast you can find out why. This lesson introduces Playwright's debugging toolkit, from the basics (console.log, screenshots) to the most powerful tool available (Trace Viewer), plus a tool that helps you write tests faster (Codegen).

## 1. Basic debugging

**`page.pause()`** — pauses the test midway and opens the Playwright Inspector so you can step through what's happening:

```typescript
test('debug with pause', async ({ page }) => {
  await page.goto('/login');
  await page.pause(); // opens the Inspector — step through code, try locators live
  await page.getByLabel('Email').fill('[TEST_EMAIL]');
});
```

**Console and network logging** — print out information to know the exact state at a given moment:

```typescript
test('log information for debugging', async ({ page }) => {
  await page.goto('/candidates');

  console.log('Current URL:', page.url());
  console.log('Row count:', await page.getByRole('row').count());

  // Log browser console messages/errors — very useful when the UI silently swallows a JS error
  page.on('console', (msg) => console.log(`[browser ${msg.type()}]`, msg.text()));
  page.on('pageerror', (err) => console.error('Page error:', err.message));
  page.on('response', (res) => {
    if (!res.ok()) console.log('Failed response:', res.status(), res.url());
  });
});
```

**Screenshots and video on failure** — configure this in `playwright.config.ts` to automatically capture evidence when a test fails, without having to reproduce it manually:

```typescript
// playwright.config.ts
export default defineConfig({
  use: {
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
    trace: 'on-first-retry',
  },
});
```

## 2. Trace Viewer — the most powerful debugging tool

A trace is a full "recording" of a test run: every action, every network request, console logs, and even **DOM snapshots** at each step — letting you replay exactly what happened, even after the test has finished running. This is especially valuable when a test fails in CI, where you can't open a browser to watch it live.

```bash
# Record a trace while running tests
npx playwright test --trace on

# Only record on retry after a first failure (recommended for CI — lighter than "on")
npx playwright test --trace on-first-retry

# Open a recorded trace
npx playwright show-trace trace.zip
```

Trace Viewer shows three main panels you should know how to read:

- **Timeline & Actions**: a list of every action (click, fill, waitFor...) in order — click any action to see the exact DOM snapshot at that moment.
- **Network tab**: every request/response that occurred during the test run — useful for spotting a slow or failing API call.
- **Console tab**: browser console logs and JavaScript errors captured during the run.

:::tip[Why Trace Viewer beats a screenshot]
A screenshot only shows you **one moment**. A trace lets you replay the **entire run** — you can pinpoint exactly which action caused the failure or which network request returned the wrong thing, instead of guessing.
:::

## 3. Codegen — generate code from real actions

Instead of writing locator code from scratch, you can have Playwright **record** your real actions in a browser and generate the matching code:

```bash
npx playwright codegen https://hr-tool-software.netlify.app
```

A browser window opens; as you click and type like a real user, Playwright shows the equivalent code live in a separate window — copy that code into your test file.

:::caution[Codegen is a starting point, not a finished product]
Code generated by Codegen usually prioritizes capturing the action quickly over locator quality — it may use a long CSS selector instead of `getByRole`. Always review and tighten up locators according to the principles from [Locators & Selectors](./05-locators-selectors/) before committing the code.
:::

## 4. VS Code Extension

Install the **"Playwright Test for VSCode"** extension to:

- Run/debug individual tests right inside the editor (click the ▶️ next to any `test(...)`), no terminal needed.
- Set breakpoints directly in your test code.
- Use "Pick locator" to point at an element on the page and auto-generate a matching locator — faster than guessing a CSS selector.
- View a trace directly inside VS Code after a test fails.

## 5. Practice exercises

1. Add `trace: 'on-first-retry'` to your test config (or a sample config you've been given), make a test fail on purpose, and open the trace with `npx playwright show-trace` to review it.
2. Use `npx playwright codegen` to record logging in to HR Tool on Staging, then edit the generated code to use `getByRole`/`getByLabel` instead of CSS selectors where applicable.
3. Install "Playwright Test for VSCode" and try running an existing test directly from the editor.
